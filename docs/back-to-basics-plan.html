2Cracks under the basics

I reproduced the first three by running the repo's own matcher and anchor code against small documents. The rest come from reading the code.

  • One bad regex blanks the app.

    A rule like ( throws inside the editor's highlight pass. There's no error boundary, so React drops the whole window. The rule and the highlights setting are both saved, so it happens again on every launch.

    Fix: validate rules on save, compile each one once and skip a broken one with a warning, and add an error boundary.

  • A lost slice heals onto the wrong text.

    Delete a slice's text and it's marked invalid, which is correct. The next unrelated keystroke maps its stale positions and marks it resolved. In my test it then pointed at " walked t".

    Fix: once a slice is invalid or ambiguous, stop mapping its positions and only re-find it by exact text plus context.

  • Highlights land on the wrong letters.

    After a double space the highlight covers " The Spir". Inside a pasted block quote it covers "The Spir". After a pasted line break nothing highlights. The matcher counts characters in cleaned-up text that no longer lines up with the document.

    Fix: match the raw text through a character-to-position map, the approach anchoring.ts already uses.

  • Save failures are invisible.From code

    A failed save still flips the label back to "Saved". The warning goes to a run log that only renders with VITE_DEBUG_PANELS=1.

    Fix: show "Not saved" with a one-line reason.

  • One document, two editors.From code

    If a slice lives in the document you're writing, opening it in the panel starts a second editor on the same text. Whichever saves last overwrites the other's edits.

    Fix: goes away with the side panel.

  • Smaller ones

    A repeated phrase records the first occurrence's offset (0 instead of 27), which weakens repair. Deleting a slice writes no history event. The title bar shows Ctrl+H, Ctrl+\ and ?, but nothing listens for them. Clicking a highlighted word opens the panel, so you can't click into the word to edit it.

3The new flow

Two authoring actions, one way to read, one way to edit.

  1. Make an entitySelect "The Spire" and choose New entity. It's saved as the regex \bThe\s+Spire\b, ignoring case, with word edges that also handle accented names like Éowyn.
  2. Add a sliceIn any document, select the paragraph, choose Add slice, and pick The Spire (or type a new name).
  3. ReadWith Entities on, hover "The Spire" anywhere. The card lists each slice's text in large type.
  4. EditClick a slice in the card. The main viewport switches to that slice's document in Edit slices mode. Drag the handles. Done, or Esc, takes you back to where you were writing.

Until the full-page entity editor exists, click the entity's name in the hover card for a small dialog: its name, one regex per line, and Delete.

4What goes away

  • The right side panel: entity chips, name field, rule form, slice cards, and the embedded document editor.
  • Everlink's four-step flow (chooser, target document, pending rails, commit). New entity plus Add slice cover it.
  • Title bar extras: brand, folder crumb, Panel, Full Screen, Shortcuts, and the key hints. The document title, the three toggles, and a save dot remain.
  • The Words / Paras / Chars row above the editor.
  • The right-click menu, and Bold, Italic and Copy in the selection bubble. Ctrl+B, Ctrl+I and Ctrl+C still work.
  • The Shortcuts page, which describes buttons that no longer exist.
  • Slice titles and "boundary mapped forward" lines in the hover card. A status appears only when a slice is lost.
  • Rule kinds, and the Whole word and Allow possessive checkboxes.
  • Thirteen interface font sizes, from 10.6px to 24px, become four. The editor goes from 17.4px to 22px; the interface runs 16px to 20px.

That's about 1,700 lines across 18 files. Nothing in the database is deleted: rules convert in a migration that writes history events, and existing slices keep working.

Stays: the editor, the document tree (larger text, fewer labels), saving and history, anchors (fixed), the hover card, and the entity chooser, which becomes Add slice.

5Order of work

  • PR 1, Core. Regex-only rules and the migration, the matcher fix, rule validation and the error boundary, anchors that fail closed, the offset fix, and a history event for deleted slices. Each starts as a failing test. Almost nothing visible changes.
  • PR 2, Quiet UI. Everything in "What goes away," the type scale, the Entities and Slices toggles, the slimmer hover card, New entity and Add slice, the entity dialog, and "Not saved." It also brings the Product Guide in line, since it still promises draggable side panels.
  • PR 3, Slice editor. Edit slices in the main viewport, working drag handles saved through the existing updateSliceBoundary call, Done and Back, and re-placing a lost slice by selecting text and pressing Place.

For each one, npm run check passes and I exercise the change in the running app. Branch and PR only; nothing merges without your OK.

Deferred: the full-page entity editor, rule-defined slice boundaries, and the multi-panel layout described in the Product Guide.

6Decisions

Drew's answers, 2026-10-27.

  1. Regex-only rules?Yes. A bare line ignores case, as before. Wrap it in slashes to set flags yourself: /\bWill\b/ matches "Will" but not "will". Recorded as ADR-008.
  2. Delete Everlink rather than hide it?Delete the code, but preserve the concept in Markdown: "If I ever released this, the concept of 'Everlink it!' is fun." See everlink-it-concept.md.
  3. The small entity dialog as the stopgap until the full page?Yes.
  4. By "delimiters," did you mean the anchor (document, positions, text), or rule-defined boundaries?"Just what was there already." A rules system might be more robust in the future, but there's no need to add complications when a competent user would likely avoid the problem to begin with. Recorded as ADR-009.
